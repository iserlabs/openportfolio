# Runbook: Recovery Key

What the offline recovery key is, the ceremony that creates it, exactly what
its 72-hour window does and doesn't guarantee, where to put it, and what to
do with it if this server is ever compromised.

Audience: same as the other runbooks — comfortable with a terminal, no
ATProto background assumed. Read this *before* you need it; the whole point
of the ceremony is that it happens once, calmly, before anything is wrong.

## The five-minute version

Your identity on the network (your `did:plc:...`) is a small signed document
hosted by the [PLC directory](https://plc.directory), not by your PDS. That
document says, among other things, "here is the server that currently hosts
this identity" and "here are the keys allowed to change this document."
Those keys are called **rotation keys**.

By default, the only rotation key your account has is the one your PDS
holds for itself (`PDS_ROTATION_KEY` in `.env`, generated by `setup.sh`) —
which means if someone compromises this VPS, they get that key too, and can
rewrite your identity document to point at *their* server instead of yours.
An **offline recovery key** is a second rotation key that never touches this
VPS at all, registered as *higher priority* than the PDS's own key — so if
the PDS's key is ever used against you, you can use this one to override it.

## The ceremony

Run automatically as phase 3 of `deploy/setup.sh` (see
[`install.md`](./install.md)) if the [`goat`](https://github.com/bluesky-social/goat)
CLI is installed on the VPS at the time. Here's exactly what happens, so you
know what you're trusting:

1. `setup.sh` logs `goat` in to your owner account **by DID**, not handle
   (`goat account login --username <did> --password <owner-password>
   --pds-host https://pds.yourdomain.com`) — deliberately DID-based since
   the handle migration earlier in setup is best-effort and might not have
   landed yet.
2. `goat key generate` produces a fresh P-256 keypair (note: this is
   goat's default curve, distinct from the PDS's own on-disk rotation key,
   which uses secp256k1 and is generated separately by `setup.sh` — both
   curve types are valid did:plc rotation keys) **entirely offline** — no
   network call, no PDS involvement. This is the only step that actually
   creates the key; everything else just registers or saves it.
3. The keypair is written to `./recovery-key-KEEP-OFFLINE.txt` on the VPS
   (`chmod 600`, owner-read-only) — both halves: the public key (safe to
   share) and the private key (**not** safe to share, ever, with anyone).
4. `goat account plc add-rotation-key --first <public-key>` registers the
   public half as your identity's **highest-priority** rotation key — ahead
   of the PDS's own key. "Highest priority" is the entire point: it's what
   makes this key able to override the PDS's key later if it ever needs to.
5. `setup.sh` prints the full explanation (reproduced below) and tells you,
   in no uncertain terms, to move the file off this server right now.

If `goat` wasn't installed when you ran `setup.sh`, this step (and the relay
crawl request that depends on it) was skipped, with instructions to install
`goat` and re-run — re-running picks up exactly here, since every earlier
step is already done. **Do this soon.** Until you do, the only thing that
can ever recover your identity if this VPS is lost or compromised is a key
that lives on that same VPS.

## The 72-hour window — what it does and doesn't guarantee

This is the exact language `setup.sh` prints during the ceremony, quoting
the [did:plc specification](https://github.com/did-method-plc/did-method-plc)
directly:

> "The PLC server provides a 72hr window during which a higher authority
> rotation key can 'rewrite' history, clobbering any operations (or chain
> of operations) signed by a lower-authority rotation key."

In practice, because your offline key was registered with `--first` (making
it the *highest*-priority rotation key — higher than the one this PDS holds
for itself): if this server is ever compromised or seized and someone uses
the PDS's own key to rewrite your identity (point it at their own server,
strip you out, whatever), **you have a 72-hour window from the moment of
that first unauthorized operation** to sign and submit a competing operation
with this offline key and reclaim control. After that window closes, the
PLC directory treats the compromised chain as final — there is no appeal
process, no support ticket, no override after the fact.

Read that carefully, because it is easy to misread as a guarantee it isn't:

- **This is a window to notice and react, not immunity.** The clock starts
  the moment an attacker acts, not the moment you notice. If you don't
  notice a compromise for a week, the window has already closed — this key
  gives you 72 hours *of opportunity*, not 72 hours *from when you check*.
- **It only helps if you actually have the key when you need it.** A
  recovery key you can't locate, or that was destroyed along with the VPS
  because you never moved it, protects nothing. See storage recommendations
  below.
- **It cannot be regenerated after the fact.** If you lose this key, you
  don't get a do-over — you've lost this safety net permanently. You can
  register a *new* offline key at any time (see below), but that doesn't
  retroactively protect you against an operation signed before it existed.
- **It's specifically about the PLC identity document** — who your DID
  currently says its rotation keys and hosting PDS are. It is not a backup
  of your content; for that, see [`restore-from-backup.md`](./restore-from-backup.md).

## Storage recommendations

The private key in `recovery-key-KEEP-OFFLINE.txt` is the single most
sensitive artifact this project produces. Treat it accordingly:

1. **Move it off the VPS immediately** — don't leave it sitting in
   `deploy/` "for now." `scp` it down, then delete it from the server:
   ```sh
   scp yourvps:~/open-portfolio/deploy/recovery-key-KEEP-OFFLINE.txt ./
   ssh yourvps 'shred -u ~/open-portfolio/deploy/recovery-key-KEEP-OFFLINE.txt'
   ```
   (`rm` alone is fine too if `shred` isn't installed — the main goal is not
   leaving a live copy on the same machine whose compromise this key exists
   to survive.)
2. **Put it somewhere that survives this VPS's total loss**, and ideally
   somewhere that survives *your* house burning down too:
   - A password manager that supports file/note attachments (1Password,
     Bitwarden, etc.) — encrypted, backed up, accessible from anywhere.
   - Printed on paper, stored somewhere physically secure (safe, safety
     deposit box). Paper doesn't get hacked remotely.
   - A hardware security key / offline USB drive kept in a separate
     physical location from the VPS's provider and from your primary
     computer.
3. **Keep more than one copy**, in more than one location, if you can — the
   failure mode you're protecting against here is total loss, and a single
   point of failure for your *recovery* mechanism defeats the purpose.
4. **Note down your DID alongside it** (`OWNER_DID` in `.env`, also printed
   at the end of `setup.sh`) — you'll need it to reference the account
   during a break-glass recovery, and it's not something you can look up
   without access to the (possibly compromised) server.
5. **Never** put it in this git repo, a cloud drive with weak sharing
   defaults, a Slack DM to yourself, or anywhere else that isn't
   specifically an intentional secret-storage tool.

## Testing the key without spending its safety net

You can verify the *public* half is correctly registered at any time,
read-only, with no risk:

```sh
goat account plc current --plc-host https://plc.directory
# or, without needing a login session:
goat plc data <your-did>
```

Confirm your recovery key's `did:key` (from the "Public Key" line in
`recovery-key-KEEP-OFFLINE.txt`) appears in `rotationKeys`, and — this
matters — at index 0 (highest priority).

You can also rehearse the *signing* half without ever submitting anything,
by signing a real update operation locally and simply not running the
`submit` step:

```sh
goat plc update <your-did> --prev <cid-of-current-op> | \
  goat plc sign - --plc-signing-key <the-private-key-from-your-file>
```
(`goat account plc current`/`goat plc data <did>` shows you the current
op's CID if `--prev` is omitted it uses the latest automatically — omitting
it is fine for a rehearsal since you're not submitting.) This proves the
key material in your backup is valid and produces a correctly-signed
operation, without touching your live identity. Do this once a year or so,
especially after moving the file between storage locations.

## Break-glass procedure (server compromised or unreachable)

This is what you actually run if the scenario the 72-hour window exists for
happens: your VPS is compromised, seized, or otherwise unreachable/untrusted,
and you need to reclaim your identity using nothing but the offline key —
**from a different, trusted machine**, never from the VPS in question.

All three commands below are fully offline-capable except the last, and none
of them depend on the compromised PDS being reachable or cooperative — they
talk to the public PLC directory directly.

1. **Figure out what the attacker changed**, so you know what you're
   correcting:
   ```sh
   goat plc history <your-did>
   ```
   This is a public, unauthenticated read against the PLC directory — safe
   to run immediately, tells you the full operation log including whatever
   was just done to your identity.

2. **Build a corrective operation, based on the last operation *you*
   trust** — not the attacker's latest one. This is the step that actually
   matters for the 72-hour window: you're not just adding your key, you're
   producing a new operation that supersedes the compromised chain.
   ```sh
   goat plc update <your-did> \
     --prev <cid-of-the-last-operation-you-trust> \
     --remove-rotation-key <the-compromised-PDS-rotation-key> \
     --pds <url-of-a-PDS-you-now-control> \
     > update.json
   ```
   Use `--prev` to point explicitly at the operation immediately *before*
   the compromise — `goat plc history` from step 1 gives you that CID. If
   you omit `--prev`, it defaults to the current (attacker-controlled) op,
   which is not what you want here.

3. **Sign it offline**, using the private key from
   `recovery-key-KEEP-OFFLINE.txt` — this step touches no network at all:
   ```sh
   goat plc sign update.json --plc-signing-key <your-offline-private-key> > signed.json
   ```

4. **Submit it directly to the PLC directory** — this is the one network
   call in the sequence, and it deliberately does *not* go through the
   compromised PDS:
   ```sh
   goat plc submit signed.json --did <your-did>
   ```

5. **Verify it landed**: `goat plc data <your-did>` should now show the
   updated rotation-key list and (if you changed it) the new PDS service
   endpoint.

After this, you still need to actually stand up a PDS you control with your
data on it — this procedure reclaims the *identity document*, it doesn't by
itself move your content anywhere. Combine it with
[`restore-from-backup.md`](./restore-from-backup.md) (if you have your own
`BACKUP_DIR` artifacts) or the relevant parts of
[`migrate-away.md`](./migrate-away.md) (if you're moving to a fresh PDS and
need the account/import steps too).

> **VERIFY ON STAGING (Task D1):** the sequence above is built directly from
> `goat`'s verified command surface (`plc history`/`plc update`/`plc
> sign`/`plc submit`, confirmed against the installed CLI's own source),
> but a real, adversarial "attacker rewrote my identity, now claw it back"
> scenario has not been rehearsed end-to-end against a live PDS +
> plc.directory in this task. Rehearse it once against a disposable
> did:plc identity before you ever need to trust it for real.
